## Evidence and candidate

Supplied retained-log audit: B1 A/B generation 22.382/22.143 seconds; G0 generation
153.595 seconds (25.09 was CPU-tier request wall); G1 generation 151.345/151.382
seconds. G1 GPU exchanges took 125.125 seconds / 2623 batches for A and 127.363
seconds / 2668 batches for B, about 47.7 ms per exchange. Combined GPU executor
service was 1.551 seconds. These supplied observations are not newly verified
measurements by this author. Time outside executor service includes transport,
codec/copy work, queueing and scheduling; it is not measured network latency alone.

At bf51f09e, GPU framing sends its 16-byte header and payload separately. CPU
transport assembles one contiguous frame. Connect helpers attempt TCP_NODELAY;
accepted worker sockets do not set it. A short outstanding header or tail can
interact with Nagle/delayed ACK while the receiver awaits a complete frame.
The repeated latency is compatible with that hypothesis, not proof of it.
The cancellation poll's 50 ms value is a timeout ceiling, not a mandatory sleep.
Public relay construction chains SSH local/reverse forwards through the approved
controller; it does not establish which relay/socket incurs delay.

The sole production change is `gpu_codec::send`: reserve one bounded frame,
append the unchanged header and payload, then call existing
`sock::send_all_controlled` once. Partial writes, cancellation and socket errors
still use that existing writer. The body copy consumes the existing shared I/O
budget; a new writer does not renew time already spent copying. Header formation
and reservation precede that budget as header formation did previously. Bounds
and error strings remain. No production TCP options, receive logic, routing,
scheduling, kernels, inference flags, cache or failure-counter changes.

Maximum requested contiguous storage is **4194384 bytes = 4 MiB + 80**:
`kGpuFrameMax` is 4 MiB + 64 payload bytes, plus the 16-byte header. This is one
additional bounded payload copy alongside the caller's payload, excluding
allocator bookkeeping/rounding. No growth occurs after the single reservation.
SETUP carries plan metadata (at most 4 MiB + 8 payload, 4194328 bytes framed),
not all assigned weights. The retained 92156-byte plan would frame to 92180 bytes.
UPLOAD remains at most 1 MiB + 60 payload, 1048652 bytes framed. Neither an 8 MiB
expert blob nor the full 17176473600-byte assigned set is staged by this change.

## Focused fixture

`gpu_frame_test` is a Linux-only target beside the existing socket fixtures.
It compiles only the test and real `gpu_wire.cpp`, `expert_wire.cpp`,
`wire_sock.cpp`, linking Threads. With native experts and GPU backends off,
it needs no ggml, CUDA, assets, cache directory or model weights. It starts no
Strata engine, CPU-arena service or CUDA worker. No GEN requests are consumed.

Default correctness entry checks original wire bytes against the CPU frame
encoder with SGW1 magic, including zero payload, error status, T=1-sized payload,
maximum SETUP and maximum sender bound. Small socket buffers and small reads
exercise partial writes; seven-byte writes exercise fragmented codec reads.
Oversize/zero-budget/pre-write and mid-write cancellation are rejected; a peer
that never reads exhausts the shared write budget. No latency threshold is a
correctness assertion. Known-source ordinary EOF, truncated header/payload and
malformed magic all refuse decoding and print distinct fixture labels.

This does not redesign production close accounting: GPU service currently
increments failures on any failed receive, including ordinary EOF/cancellation.
Client close does not send GPU_STOP. Thus failures=1 is plausibly teardown, but
the historical cause remains unconfirmed; fixture labels do not retroactively
identify it. CPU service handles non-malformed closure differently.

`--latency` uses one persistent TCP connection per arm, in fixed order:

1. Original bf51f09e split sender on both ends, accepted NODELAY off.
2. Candidate real contiguous sender on both ends, accepted NODELAY off.
3. Original split sender, accepted NODELAY on **only in the fixture**.

Client NODELAY is checked in every arm; accepted settings are checked too.
Each connection runs a control shape and T=1, T=2, T=8 inference shapes at
K=10, H=2560. Each shape has one excluded warmup and eight measured exchanges:
32 measured + 4 warmups per arm, 96 measured frames across three arms. The
dummy executor returns deterministic finite floats; real request/reply codecs,
binding/digest checks and exact response bytes are validated. No asset plan is
loaded: the dummy uses only fixed identity/geometry fields for codec validation.

Report per-shape request/reply bytes, median, empirical p95 and maximum RTT,
plus each arm's measured RTT sum and separate elapsed time including warmups.
Eight observations give coarse tails (p95 equals maximum), not a statistical
performance guarantee. Fixed order, scheduling and relay variance are limits.
No automatic speedup threshold, retuning or repeated campaign is authorized.
Loopback negative results do not reject a relay-specific interaction.
